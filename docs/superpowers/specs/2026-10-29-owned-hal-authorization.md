# HAL native authorization boundary

Recommendation: add a small, stage-bound request/reply protocol serviced by the existing native HAL owner. Keep historical clock queries at 20 ms. A consumed ledger row is not a fresh native authorization. Do not claim a Python lock makes native state atomic with tracker mutation, queue insertion or HTTP delivery.

Status: adopted by the controller before authorization implementation, following independent design review. This is an addon-only fixture contract. Its deadlines are stricter authorization limits, not changes to clock, source or captured acceptance tolerances. Original design review performed no implementation or runtime actions. Paths and line numbers describe inspected code and may move.

## Concrete existing boundaries

- `owned_ad_playback.py:156–185` holds `provider.lock`, then calls `provider.authorize(evidence, decide)` before changing `_consumed`, `_evidence` and the tracker. The tracker calls `_enqueue` synchronously during this action.
- `owned_ad_playback.py:134–154` performs another authorization immediately around `worker.enqueue`, and supplies an additional delivery-time authorizer. `ad_tracking.py:284–295` invokes that third authorizer before HTTP, outside the worker queue lock.
- `owned_clock.py:424–432` only rechecks a local snapshot/generations/freshness. It cannot see a native-only pause or route fence since the last consumed row. HAL must have a distinct implementation; changing this AE method is unnecessary.
- `ad_tracking.py:75–90` marks an event emitted before invoking enqueue. A rejected enqueue is already non-retryable. Preserve that property, but report native rejection accurately rather than as a nonexistent endpoint.
- The native `RunOwnedHal` owner in `StreamManager.cpp` drains callback evidence into `AppliedControlView`, reads controls, checks guards and sleeps 5 ms per normal iteration. `HalCore::NativeState()` loads the independent atomic native gate; route listeners retire that gate. `DesiredIntent()` is an owner-updated atomic, while callback-applied state is obtained from drained records. No callback I/O or new realtime machinery is needed.
- Existing immutable transport helpers already pin private directories, use bounded no-follow reads, exclusive publication, and identity checks. Do **not** copy the full-history directory-scan approach of `PollGain` into a 50 Hz authorization path.

## Minimal transport and interfaces

Use a new pinned private `authorization/` subdirectory of the existing session. Both sides retain its identity; 0700 directory and 0600 regular single-link files, original UID, no symlinks. Exact filenames are `request-NNNNNN.json` and `response-NNNNNN.json`, where N is a strictly sequential nonzero request ID. Publish each completely through a private temporary file and exclusive atomic rename. Native checks only the expected next request; Python checks only its exact pending response. No listing, full scan, overwrite, deletion, or old-file revalidation on the live path. Original bytes and hashes remain evidence for the offline audit.

One authorization-I/O mutex shared by the existing monitor and beacon worker permits **one outstanding request total**, including request publication through reply consumption. Acquire/wait only outside provider, tracker, gain-controller and worker locks. The existing two callers need no additional worker thread: a bounded slot wait counts against the same request deadline. Callback/control methods never wait for this mutex. A dedicated transport method must not invoke normal `poll(provider)` from the beacon worker or concurrently consume the ledger.

Minimal interfaces (names illustrative):

- Python `transport.probe(stage, evidence, expected_local_generation, event_key=None, decision_id=None, parent_proof=None, deadline_ns=...) -> immutable Proof | Rejection` performs bounded I/O outside state locks.
- Native `PollNextAuthorization()` returns zero/one bounded validated request, `CheckAuthorization(request, clock_cache, applied_view, core, now)` performs the fresh check, and `PublishAuthorizationReply()` publishes the decision. All run on the existing non-realtime owner.
- Python `provider.consume_proof(evidence, proof, stage, action)` validates and consumes a single-use proof and runs only a bounded in-memory action under `provider.lock`. It never performs transport I/O or waits.

Requests/responses are each at most 4096 bytes with exact schema, bounded integers/strings, no URLs. The session request-count ceiling is 32768, sufficient for the bounded fixture and its 50 Hz tracker checks; exhaustion fails authorization closed, never wraps IDs. A response echoes request ID and raw request hash, exact stage, complete binding, original query sequence/hash/q/bracket, segment hash, expected effective tuple, startup S0/provenance/deadline if applicable, and event/decision digest for queue/dispatch stages. Response also contains result/reason, native check start/end, actual gate/intent, applied evidence identity, callback freshness timestamp and lease expiry. A bounded native cache of emitted query identities validates the original query independently of request assertions; expired/evicted references reject without remapping.

Stages are `tracker`, `queue`, `dispatch`. A tracker proof cannot authorize an event; a queue proof binds one exact immutable event intent and its preceding tracker decision/proof; dispatch binds that same event and successful queue proof. Each stage has a fresh request ID and response. An immutable event key includes session, placement/event, exact URL digest, original query identity and decision ID. Do not place raw URLs in native telemetry.

## Fresh native check and precise linearization

Service authorization independently on every normal owner iteration, rather than only when the next 20 ms clock query is due. Do not call the stateful clock `Query()` for a probe: that could change readiness/reacquisition counts or create extra clock observations. Probe validates an already emitted query and current authority only.

After request read, take a **fresh** time; validate its expiry and binding. Run the existing device/ownership checks, drain and preserve acquired callback evidence, and compare the requested tuple with current applied device/stream/playback/gain epochs and native gate/intent. Require unmuted nonzero gain, current acknowledged playing state, no pending genuine effective change, live applied lease and callback-entry age ≤40 ms. An unchanged renewal may advance transport revision without invalidating the effective tuple, but only an actually acquired renewal supplies a later lease. Check terminal/stop/error state and final source END. Existing source mapping, original q freshness and unique segment qualification remain mandatory.

The **final atomic native-gate load**, after these owner-owned validations, is the authorization linearization point L. Require it to equal the initially read gate and the query's gate and contain neither paused nor retired. The owner does not mutate intent/applied owner state during this check; check intent consistency too. Monotonic gate epochs prevent pause/resume ABA. Route/native stop/retirement must reach this gate before they count as effective native fences; confirm every relevant asynchronous path already does so, or add a small addon-only gate closure at the source of any uncovered invalidation. Unrelated booleans sampled earlier cannot substitute for that ordering proof.

Bracket L with fresh Mach check-start/check-end timestamps; do not invent an exact timestamp for an atomic instruction. Require the check bracket ≤5 ms. Response records this interval and its gate value. Native state changed **before L** rejects. A change **after L** may race an already authorized action; subsequent Python checks can reject a known change but cannot prove no unseen native change occurred. This is the explicit unavoidable cross-process boundary. Native emits no HTTP and does not hold the callback or native gate while Python acts.

Final callback delivery may continue to publish unchanged-epoch records during the check; that does not invalidate a historical mapping. A genuine changed applied tuple cannot be silently accepted from undrained callback-owned memory: owner intent changes invalidate the old query before publication, and native gate changes invalidate it independently. Terminal/lease checks use actual fresh check-end time and constrain proof expiry.

## Strict, predeclared budgets

Binding protocol limits: request start-to-consumption ≤20 ms, native check bracket ≤5 ms, and Python action time no later than native check-end +5 ms. These are **new stricter authorization liveness limits**, not new clock tolerances; freeze them before tests/captures and do not fit them to a failed run. A filesystem stall can exceed a wait target, so resample time after every read/write/lock acquisition and reject late results; no syscall-duration guarantee is claimed.

Every proof/action also remains within original q +100 ms, the current acknowledged gain lease (strictly before expiry), and any terminal/source-END restriction. For initial qualification/impression/start carry the exact rational S0 +120 ms deadline through all evidence and enforce it at actual Python mutation/decision and queue insertion. **Dispatch does not restart or extend that deadline:** it verifies the preserved decision/queue times satisfied D0 and performs its fresh current-state check within the original q +100 ms and its own short exchange limits. D0 is not silently extended into a new HTTP receipt deadline, nor silently made an additional dispatch-time cutoff. A separately requested stricter dispatch cutoff would be a new restriction. Actual HTTP receipt remains separately measured and is not claimed bounded by this authorization protocol.

Set the request absolute deadline to the minimum of request-start +20 ms, original q +100 ms, known lease/terminal limits and the initial deadline when stage is tracker or queue. On reply, additionally cap consumption by check-end +5 ms. Validate causal ordering: request-start ≤ native check-start ≤ check-end ≤ receive/action time, with checked arithmetic and rejection of future or regressed times. Queue-lock wait, native service time, file publication and reply delivery all consume these budgets. Ordinary event threshold-to-decision remains ≤141.333333… ms in the independent evaluator; the handshake never extends it.

The native loop's existing 5 ms sleep makes several short handshakes plausible, but does not guarantee them. Initial impression and start each have separate queue/dispatch checks; tracker plus both queue checks must fit the roughly 78 ms remaining to D0 after worst-phase startup eligibility, while dispatch checks retain the original q-freshness deadline. Three maximally slow 20 ms exchanges can consume 60 ms; native contention, Python work and optional interleaved dispatch consume remaining slack too. If measured scheduling cannot meet the frozen budgets, fail the experiment; do not replace this with stale proof reuse or timing relaxation. A bounded event-batch optimization can be reviewed later, but is not needed in the first minimal protocol.

Gain/control work has priority between probes. If gain reconciliation shares the monitor owner, service due renewal and flush queued playback controls before taking the authorization slot and again between staged events; do not drain an arbitrary snapshot/event backlog first. At most one short probe may delay the next renewal check; do not enter an RPC gain read while holding the auth-I/O mutex. The gain owner's ≤50 ms read bracket and 100 ms nominal cadence remain unchanged, and synchronous pending-change invalidation must happen before its transport publication. Native serves one request only after its normal control/gain/guard/evidence work; authorization traffic cannot skip that work or monopolize the loop. Under overload, reject/interrupt stale tracking work rather than starve leases, burst observations, or delay native fences. This ordering needs explicit integration tests, not a claim that the 500 ms lease tolerates any loop arrangement.

## Tracker versus actual queue changes

Refactor the HAL bridge only; the current nested synchronous structure cannot safely host a blocking probe.

1. Validate a new snapshot locally, obtain its tracker proof **outside** `provider.lock`, then reacquire the lock and check local generation, synchronous Python playback/gain intent, cancellation, evidence identity, all times, and proof stage/single-use identity. Immediately before tracker mutation take actual decision time. Do not use native L or response time as the Python decision timestamp.
2. During this one bounded tracker call, `_enqueue` collects bounded immutable **event intents only**; it must not contact native or enter the network worker queue. Bind each to the original evidence and actual decision. Preserve the tracker's emitted/dedup state. Mark audit outcomes `pending_native_queue_authorization` until actually resolved; staging must never be reported as actual queued success.
3. Release the provider lock. For each staged intent obtain a separate queue proof. Reacquire the lock, recheck current Python state and fresh time, consume the exact proof, and call bounded `worker.enqueue`. No file I/O under the lock. Record actual queue result and time separately from original decision. Rejection permanently drops this intent; never roll back emitted state or replay the old sample to generate it again.
4. The existing beacon worker obtains its separate dispatch proof outside all state/queue locks, then briefly reacquires the provider lock for local checks and consumes it. Release the lock before HTTP as today. This preserves the existing final defense for time spent queued. HTTP may already be authorized when a later native fence occurs; retain cancellation behavior and the explicit linearization limitation.

If the **pre-tracker** proof is rejected, do not mutate normal tracker progress or revisit that evidence later. Advance a separate attempted/discarded-row cursor and mark a continuity interruption so a later valid sample cannot backfill crossings through the rejected interval. Calling the existing interruption mechanism under lock is an explicit conservative invalidation, not acceptance of the sample. For post-decision rejection keep the emitted event terminal and mark the relevant interval interrupted/ambiguous as appropriate; preserve the original decision with a negative authorization result. Missing required events must still fail acceptance.

## Teardown and races

- Python pause/stop/route/gain-intent change bumps local authority synchronously; every outstanding proof carries that expected generation. A response cannot clear or overwrite newer local state. Unchanged gain renewals do not reset authority.
- Native pause before L rejects even if Python has not received its callback. Pending genuine owner gain/playback intent rejects before callback application; route listener closes native gate. Resume changes native epoch, so an old proof cannot revive after resume.
- A response published after L but before a new fence is historical proof at L only. If Python knows the new fence before action it rejects; otherwise the explicit after-L race applies. A second queue/dispatch proof must independently see current native state.
- Retire/close cancels waiters immediately without waiting for the auth-I/O mutex; wake polling waits, invalidate local generation and never act on late replies. Transport file descriptors stay owned until the bounded active operation unwinds, then close—avoid closing/reusing an FD from another thread while a read is in progress. Never hold session lifetime hostage to a reply.
- A timed-out request ID is terminal. The simplest safe policy retires authorization for that session on protocol timeout/malformed/replaced transport, with no successor request or retry; native may still write its one late reply, which remains evidence. A clean state-mismatch rejection may advance to the next exact ID, but the rejected sample/event cannot be retried.
- Native exit stops serving requests. Cancellation/EOF produces no new positive proofs; outstanding callers expire/cancel. No cleanup, background request service, or response write is moved into IOProc/listeners. Retained native context safety rules stay unchanged.
- New session/incarnation uses a new pinned namespace and counters. Never accept a late response using only request number or a reused pathname. Pinning, full binding, request digest, stage and event identity all must match.

## Focused tests before integration/capture

1. Pause/route/native retirement after last ledger query but before L rejects without relying on a Python callback; fence after L is explicitly classified, and a subsequent queue/dispatch probe rejects.
2. Pause/resume ABA, genuine gain intent before applied acknowledgement, unchanged acquired renewal, and new incarnation; exact tuple/provenance and lease behavior.
3. Deterministic fence schedules before/inside/after native bracket and Python lock reacquisition; local gain/pause callback during file wait runs promptly and invalidates the proof. No nested lock wait or callback I/O.
4. Tracker rejection causes no sample progress/event production/backfill; queue and dispatch rejection retain emitted/dedup state and explicit negative audit. Staged intent is not counted queued/delivered.
5. Separate stage/event/URL-digest binding, single-use proofs, replayed IDs, forged original query hash, missing/evicted cache entry, response-before-request/future timestamps, partial/oversize/mutated/symlink/replaced files, count exhaustion and duplicate exclusive publication.
6. Exact deadline boundaries for 20 ms exchange, 5 ms native bracket, 5 ms consumption, original q +100 ms, callback age ≤40 ms, gain expiry, rational S0 +120 ms and source END. Time sampled after transport and lock work; no loop-entry timestamp reuse.
7. One outstanding request with simultaneous monitor and beacon worker; no ledger-consumer race, no growing pending-request queue, and bounded operation/teardown. Timed-out late response never acts or resumes the session.
8. Initial impression/start through tracker, queue and dispatch checks with normal 20 ms observations and delayed replies; original q/source/hash retained and actual decision times audited. Existing nine-query reacquisition and frozen v2 unchanged.
9. Before any capture, benchmark this exact path with a maximum-populated session: all allowed old authorization files plus maximum retained control/gain records, maximum allowed clock/evidence row sizes, and concurrent monitor/worker probes with due gain renewal. Record per-stage request-to-action latency, native bracket, reply age, slot wait, control/renewal cadence, original-q age and initial decision/queue deadline results. Demonstrate constant-count authorization directory accesses and no full auth-history scan. Preserve every rejected/late attempt; do not report only successful percentiles. The benchmark may establish observed feasibility, not an OS scheduling guarantee, and must run outside capture windows.

Alternatives rejected for this first version: reuse latest drained row (known race), RPC under provider lock (blocks controls), native HTTP (unnecessary responsibility), shared-memory C++ atomics read by Python (unsupported memory-model/lifetime assumptions), and piggybacking fresh checks only on the 20 ms periodic query (avoidable extra latency and risk of changing qualification counts).
