# Kodi 22 HLS end-of-stream and ad-clock evidence — 2026-11-19

**End-of-stream stall: root-caused in stock FFmpegDirect; natural EOF with no
gap verified on Kodi 22 RC2 with the timeshift-startup-eof patch. Stock
FFmpegDirect still stalls. Production success beacons: DISABLED.**

This follows the [2026-10-30 capture](kodi-owned-clock-beacons-2026-10-30.md),
which stalled at player time 260.408 seconds after the final fixture segment.
All runs here use the shipped add-on's **Test ad tracking** launch
(`launch_fixture`, VideoPlayer, FFmpegDirect timeshift) with the
`/source/late-break/` fixture: 128 live-window source segments (six-segment
window advancing every 2.005333 seconds, `EXT-X-ENDLIST` only in the final
window), a four-second preroll, and a VAST replacement of source070–071, past
the 64-output retention boundary. They test the loopback fixture only — not a
public station, production VAST inventory or physical speaker output.

## Environment

- Kodi 22.0 RC2 (`20261109-d686683a55`), macOS arm64, isolated portable
  profile under `sandbox-exec`, launched through LaunchServices so the capture
  helper can identify it. Installed Kodi 21.3 untouched.
- FFmpegDirect from the Kodi Piers repository, osx-arm64: stock 22.2.10 and
  22.2.11. Their `src/` trees are identical (22.2.11 changes only build
  dependencies and its version string).
- Patched FFmpegDirect: `realtime-override` + `timeshift-startup-eof` from
  `docs/patches/`, applied to the 22.2.10-Piers and 22.2.11-Piers tags. Both
  apply cleanly. Built locally against the Kodi dev-kit (inputstream API 3.4.1)
  and FFmpeg 9.0.2 static libraries. These lab builds are not distributed.
- Process audio from the signed Kodi Audio Capture helper (48 kHz stereo);
  Kodi JSON-RPC polled every 250 ms with notifications; all on the
  `mach_absolute_time` clock shared with the fixture server's tracking history.
- Add-on with this change's FFmpegDirect version gate (package SHA-256
  `67f72336e23dd9000e72d904d753455833acfdbf2fe9cd1149cbe05abf45749b`; runs 1–4
  used the same source before that gate change).

## Does the merged `hls-eof-stall` change fix it?

Not on its own. PR #5 sets `inputstream.ffmpegdirect.terminal_eof=true` on the
buffered route. Stock FFmpegDirect does not list that property, so Kodi drops it
(`Num Props: 2` in both stock runs; `Num Props: 3` with the patch). Stock
`TimeshiftStream::DemuxRead` returns an empty packet whenever its buffer is
empty and never returns `nullptr`, so VideoPlayer never sees end of stream.
22.2.11 has the same code. The add-on cannot make stock timeshift report EOF.

## What this establishes and what remains

- The 2026-10-30 stall is FFmpegDirect timeshift never reporting EOF, not the
  relay, playlist or add-on. With the patch on either 22.2.10 or 22.2.11, the
  same add-on route ends naturally with no gap on Kodi 22.
- Stock FFmpegDirect (what Kodi 22 installs) still stalls in caching after a
  finite source ends; the user must stop playback. This route is offered only
  for loopback fixture compositions, so ordinary stations never reach it. The
  fix belongs upstream in `xbmc/inputstream.ffmpegdirect`.
- The add-on's qualified clock is bound to the actual add-on playback session
  and survives a moving live window and both ad discontinuities in this
  fixture. A public station's live source clock has not been tested.
- Seek in either direction permanently suppresses later success events, and an
  interrupted ad is never backfilled.
- The capture helper's target validation stopped two recordings while Kodi kept
  running. Their audio before the stop is valid; the cause is not investigated.

No production VAST tag or tracking host was contacted. Production beacons stay
